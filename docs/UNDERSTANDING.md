# Understanding Kernel

## 1. 要做到「像 ChatGPT 一樣理解」，需要四件事同時成立

### 高能力語言模型

架構不能把弱模型變成強模型。複雜、含糊、跨領域的自然語言，應由高能力模型負責理解與高層規劃；本地模型負責隱私敏感、重複和專用工作。

### 高質量 Context

模型只有看到正確資料，才可能理解正確。每次對話前建立 `ContextPack`，而不是把全部歷史粗暴塞進 prompt。

### 明確的推理契約

模型不能只輸出一段「看起來合理」的文字。它必須輸出可驗證的 `IntentContract`，把事實、推測、限制、成功標準和風險分開。

### 真實回饋與評測

每次「不是這樣」「繼續」「像上一版」都是高價值訓練資料。系統需要把糾正轉成 eval 和經過審核的記憶，而不是只保留聊天記錄。

## 2. ContextPack

`ContextPack` 是這一次理解可使用的、帶來源的最小上下文，包括：

- 當前訊息與對話摘要；
- 當前活躍 GoalRun；
- 相關個人偏好與硬限制；
- 最近的項目狀態、決定、失敗與糾正；
- 即時工具證據，例如 Git branch、失敗測試、Calendar、Email；
- 互相衝突的資料；
- 每條證據的來源、時間、置信度和敏感級別。

檢索排序至少考慮：

```text
相關性 × 時效性 × 來源權威 × 置信度 × 當前作用域
```

使用者明確陳述與糾正高於模型推測；即時系統狀態高於過期摘要。

## 3. IntentContract

Planner 永遠不直接讀原始自然語言。它只接受以下結構：

```text
literal_request       使用者原話
primary_goal          主要目標
inferred_need         更深層需要
why_now               為什麼現在要做
desired_outcome       期望結果
target_scope          對象與允許範圍
constraints           不能違反的限制
preferences           風格與偏好
non_goals             明確不做什麼
success_criteria      如何證明完成
assumptions            系統正在作出的推測
missing_information   缺失但可能重要的資訊
risk / reversibility  風險與可逆性
autonomy_mode         建議、預覽或執行
confidence            整體理解置信度
evidence_ids          支持理解的來源
```

## 4. 最少提問政策

系統不應因為有任何不確定性就把問題丟回給使用者。

### 直接執行

- 目標清楚；
- 風險低；
- 操作可逆；
- 成功標準可驗證。

### 帶假設執行

- 有輕微歧義；
- 假設錯誤的代價低；
- 可以快速回滾；
- 系統清楚標記採用的假設。

### 先給預覽

- 中等風險；
- 涉及較大範圍修改；
- 使用者可能更重視風格或主觀品質。

### 只問一個問題

只有當缺失資訊會讓任務無法成功，或高影響假設無法安全回滾時，才問一個最能消除歧義的問題。

### 必須批准

外部發送、付款、刪除、公開發布、不可逆設備操作等，不能由模型自行授權。

## 5. 對你常用語句的處理方式

### 「繼續」

先找當前 session 的活躍 GoalRun；沒有時再查最近未完成且上下文一致的項目。只有多個候選接近時才提問。

### 「這個不對」

`這個` 應指向當前正在展示或最近產出的 artifact；`不對` 觸發差異診斷，讀取此前偏好和本輪驗收標準，而不是只做關鍵詞分類。

### 「做得專業一點」

把「專業」操作化成該任務的 rubric，例如信息層次、準確性、視覺一致性、行業格式與可驗證性；若已有過往糾正，優先使用個人 rubric。

### 「今天做什麼」

這不是泛泛建議題。系統要結合日程、截止日期、當前項目阻塞、長期目標與可用時間，輸出唯一主目標、理由和第一個可執行步驟。

## 6. 記憶不是聊天全文

長期記憶必須是結構化、可撤銷、可過期的記錄：

```text
kind
value
source_event
source_authority
confidence
valid_from / valid_to
sensitivity
status: proposed / confirmed / superseded / expired
```

模型先產生 `MemoryProposal`；政策與使用者糾正決定是否寫入權威存儲。

## 7. 理解評測

每個 case 至少定義：

- 使用者原話；
- 當時可用上下文；
- 正確 primary goal；
- 必須保留的限制；
- 禁止作出的推測；
- 應否提問；
- 應使用的能力；
- 成功標準。

理解模型或 prompt 的任何變更都必須跑完整 eval，避免修好一種表達卻破壞另一種。
